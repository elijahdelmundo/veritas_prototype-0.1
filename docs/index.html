README.mdVERITAS · PROTOTYPE 0.1

Veritas Prototype 0.1

Vista Care is a six-branch clinic dashboard with a Flutter frontend and Laravel 12 REST API. Laravel stores local data in SQLite; Flutter displays reports, inventory, branches, and calculated summaries.

Layout

frontend/        Flutter UI, HTTP client, models, tests, platform projects
backend/         Laravel API, models, migrations, seeders, tests
scripts/         Windows helpers for XAMPP PHP and Composer
.vscode/         Flutter launch configurations
.github/         Flutter/Laravel CI and GitHub Pages workflow

Keep the repository root open in VS Code. Run Flutter commands from frontend; run the Windows helpers from the root.

1. Start Laravel

The installed setup uses XAMPP PHP 8.2 and Laravel 12. Helpers locate PHP on PATH or fall back to C:\xampp\php\php.exe, and enable the installed ZIP extension for Composer when needed without editing global PHP settings.

For this installed project, run:

.\scripts\artisan.cmd migrate
.\scripts\artisan.cmd db:seed --class=ClinicDemoSeeder
.\scripts\artisan.cmd serve --host=127.0.0.1 --port=8000

Seeding creates six sample branches, 180 reports, and 36 batches. Rerunning the seeder preserves existing report and quantity edits.

Useful URLs:

  • http://127.0.0.1:8000/ — Laravel welcome page.
  • http://127.0.0.1:8000/up — framework health.
  • http://127.0.0.1:8000/api/v1/branches — REST branch data.
  • http://127.0.0.1:8000/api/v1/reports — stored daily reports.
  • http://127.0.0.1:8000/api/v1/medicine-batches — stored inventory.

2. Start Flutter

In another terminal:

cd frontend
flutter pub get
flutter run -d chrome

This now connects to Laravel by default. Report and inventory edits persist in the database across app restarts. Failed connections show Retry; failed saves preserve form input.

For the full browser layout:

flutter run -d chrome --dart-define=DEVICE_PREVIEW=false

Default API URLs:

Client URL
Chrome / desktop / iOS simulator http://127.0.0.1:8000/api/v1
Android emulator http://10.0.2.2:8000/api/v1

Override for another server:

flutter run -d chrome --dart-define=API_BASE_URL=http://127.0.0.1:8000/api/v1

A physical phone or another computer needs a reachable development host address; its localhost is not your computer. Intentional LAN testing also requires a server bind such as --host=0.0.0.0, network/firewall access, and an appropriate browser-origin policy. Native iOS still needs device testing.

3. Try persistence

  1. Open Daily reports, edit today's Pasig report, and save.
  2. Reload Flutter: the edited report is fetched from Laravel.
  3. Open inventory and restock a batch or set its on-hand quantity.
  4. Reload again: the quantity and expiry are retained.
  5. Use the header refresh action to fetch another client's committed changes.

This is request/response synchronization, not live push updates. Users must connect to the same backend to share data. Separate local SQLite files on groupmates' computers remain separate databases.

Explicit offline/design demo

To view the design without running Laravel:

cd frontend
flutter run -d chrome --dart-define=USE_DEMO_DATA=true

Only this explicit mode creates in-memory sample data and resets on reload. A connection failure in API mode never silently switches to demo mode.

Device Preview starts with iPhone 16 in debug. Open Dart: Open DevTools and the device_preview extension to change devices. It is a layout simulation, not an actual iOS runtime.

Fresh clone setup

Install Flutter, PHP compatible with Laravel 12, and Composer. With PHP and Composer on PATH, run this from the root:

cd backend
composer install
Copy-Item .env.example .env
php artisan key:generate
if (-not (Test-Path database/database.sqlite)) { New-Item -ItemType File database/database.sqlite }
php artisan migrate
php artisan db:seed --class=ClinicDemoSeeder
php artisan serve --host=127.0.0.1 --port=8000

Do not overwrite an existing .env or regenerate an existing application key when following fresh-clone instructions. On this XAMPP computer the root helpers can replace php artisan and composer commands.

Local backend/.env, application keys, SQLite data, vendor, and frontend build/caches are ignored. Commit migrations, .env.example, source, and lockfiles. No Node build is needed for the current API.

Database and access boundary

SQLite is the exercised local database. XAMPP MySQL can be configured later by creating a database, changing Laravel's DB_* environment values, and running migrations; it has not been verified by this integration.

The prototype API is enabled only in Laravel local/testing environments. It has no login, user/branch authorization, medical records, approval workflow, or audit log yet. CORS accepts browser origins on localhost and 127.0.0.1; it is not an authentication mechanism.

Use sample data locally. Before public multiuser deployment, implement identity, server-enforced permissions, HTTPS, and the required audit rules.

Verification

From frontend:

flutter analyze
flutter test

From the root:

.\scripts\composer.cmd validate --strict
.\scripts\composer.cmd check-platform-reqs
.\scripts\artisan.cmd test

GitHub Pages

https://elijahdelmundo.github.io/veritas_prototype-0.1/

Pages hosts only the Flutter frontend and cannot execute Laravel. The workflow builds from frontend with explicit demo mode:

flutter build web --profile --dart-define=HOSTED_PREVIEW=true --dart-define=USE_DEMO_DATA=true --base-href /veritas_prototype-0.1/

The hosted iPhone design demo resets on reload and does not connect to a visitor's localhost. A real shared API requires separate PHP-capable hosting and a deployed frontend configured with its HTTPS API URL.

Architecture

Veritas Prototype 0.1 · Vista Care clinic administration Current implementation: 18 October 2026

Related documents: Workflows · Product requirements · Design system · Setup

01 · System overview

The project uses Flutter for the frontend, Laravel 12 for the REST API, and a database accessed through Laravel's Eloquent ORM. Local development uses SQLite. Flutter never connects directly to the database.

The current integration persists branch information, daily reports, and medicine batches. Authentication, clinical records, billing transactions, approval workflows, and audit trails remain future work.

The project folder is veritas_prototype 0.1, its Flutter package remains demo_demo, and the visible product brand is Vista Care.

02 · Technology stack

Layer Current implementation
UI Flutter / Dart; Material 3 and shared custom widgets
UI state ChangeNotifier, ListenableBuilder, page-local form/filter state
HTTP Dart http package; JSON requests/responses and 12-second timeout
API Laravel 12 / PHP ^8.2; versioned routes under /api/v1
Persistence SQLite locally; Laravel migrations and Eloquent
Optional database XAMPP MySQL can be configured later; not exercised by this integration
Motion Flutter animations and Cupertino page transitions
Preview Device Preview 3, iPhone 16 by default in debug
Verification Flutter unit/widget tests; Laravel feature tests and PHPUnit
Web hosting GitHub Pages for the explicit sample-data frontend only

Laravel 12 was selected for the installed XAMPP PHP 8.2. Composer installs locked backend dependencies. There is no handwritten JavaScript bridge between Flutter and Laravel: the boundary is an ordinary HTTP REST API.

04 · Data ownership and schema

Laravel's database is the authority in API mode. ClinicStore.remote keeps a UI snapshot and calculates visible aggregates; it is not durable storage. The original in-memory store remains available for tests and explicit demos.

Table Important fields Integrity
branches ID, unique name, address, target, growth, staff JSON Unique branch name
daily_reports Branch ID, date, patients, revenue, expenses, notes Foreign key; unique branch/date
medicine_batches Branch ID, name, quantity, unit, expiry, threshold Foreign key; one row per batch

Reports use database decimal columns with two fractional digits. API decimal amounts are returned as strings and parsed into Dart doubles for display and aggregation. The UI displays whole pesos in summary cards and retains two decimal places when editing reports.

Staff entries and ratings are illustrative JSON embedded in a branch; they are not authenticated user accounts, live attendance records, or a review submission system.

ClinicDemoSeeder initializes six branches, 30 reports per branch, and six medicine batches per branch. It uses first-or-create behavior so rerunning it preserves existing quantities and report edits. It is an explicit development operation, not something performed on each app launch.

05 · REST API contract

All requests use Accept: application/json; writes also use Content-Type: application/json. Successful responses wrap values in {"data": ...}.

Method Endpoint under /api/v1 Purpose Success
GET /branches Branch metadata and sample staff 200
GET /reports Persisted daily reports 200
PUT /branches/{id}/reports/{YYYY-MM-DD} Create/replace report for branch/date 200
GET /medicine-batches Persisted inventory 200
POST /medicine-batches Create a distinct medicine batch 201
PATCH /medicine-batches/{id} Restock or set on-hand quantity 200

Report write body:

{
  "patients": 42,
  "revenue": 35000.25,
  "expenses": 12500.50,
  "notes": "Daily review completed."
}

Batch creation requires branch_id, name, quantity, unit, expiry (YYYY-MM-DD), and threshold. The server assigns the ID.

Stock write bodies:

{"operation": "restock", "quantity": 10}

{"operation": "set", "quantity": 25}

Restocking adds to the server's current quantity inside a transaction with a row lock. A correction explicitly replaces the on-hand amount. Stock quantities and thresholds must be nonnegative integers; restock amounts must be positive. The supported stock limit is 1,000,000,000.

Reports require nonnegative integer patients and nonnegative monetary amounts with at most two decimal places. Patient count is capped at 1,000,000 and monetary amounts at 999,999,999,999.99. Notes are optional nullable text, capped at 5000 characters. Future report dates are rejected. New batches cannot have expiry before the Philippine clinic day.

Validation errors return 422 with field errors. Missing resources return 404. The local-only environment gate returns 503 outside local/testing.

There are no delete endpoints, authentication endpoints, pagination, websocket subscriptions, or clinical/billing APIs in this version.

06 · Frontend request and save lifecycle

Startup and refresh

  1. Resolve API_BASE_URL before Device Preview changes simulated platform behavior.
  2. Create a remote store unless USE_DEMO_DATA=true was explicitly requested.
  3. Fetch branches, reports, and batches with three GET requests.
  4. Replace the UI snapshot only when all requests succeed.
  5. Display the dashboard after data is ready.

Startup shows loading or connection/retry screens. An empty database produces a no-branches state. A failed refresh retains the last successful snapshot and shows an error; it never silently switches to sample mode.

The refresh action requests a new snapshot. Other clients' changes appear after refresh/reload; this is not real-time push synchronization. The three GET requests are independent and do not guarantee a transactionally consistent snapshot during concurrent edits.

Mutations

  1. Validate the form locally.
  2. Disable duplicate submission and keep entered data in place.
  3. Send the request and wait for Laravel's validation and database write.
  4. Update local state using the server's returned record and ID.
  5. Close the dialog only on success.

Rejected, timed-out, or disconnected saves show an error and retain the form. Transport timeouts can have ambiguous outcomes if a write reached the server; automatic retries and exactly-once mutation guarantees are not implemented. Report PUT is naturally keyed by branch/date; batch creation and restocks should be checked before retrying after an uncertain response.

Stock corrections and report edits currently use last-write behavior. Version conflicts, full inventory event history, and audit records remain future requirements.

07 · Local networking and access boundary

Client Default API base URL
Chrome / desktop / iOS simulator http://127.0.0.1:8000/api/v1
Android emulator http://10.0.2.2:8000/api/v1
Physical device / another computer Supply the development server's reachable LAN URL

Override with --dart-define=API_BASE_URL=http://HOST:8000/api/v1. The default server binds to loopback. Shared LAN testing requires an intentional server bind and reachable host/firewall configuration.

CORS accepts browser origins on localhost or 127.0.0.1 with any port. Other browser origins are rejected. CORS is a browser policy, not user authorization. Android debug/profile permits local HTTP; release Android keeps its normal transport policy. macOS client networking is enabled. Native iOS and physical-device behavior still require device validation.

This is a local development API without authentication. Routes are enabled only in Laravel's local/testing environments. Do not change the environment gate to expose clinic writes publicly without implementing authentication and resource/branch policies.

08 · Deployment and demo behavior

GitHub Pages cannot execute PHP. Its workflow deliberately builds Flutter with USE_DEMO_DATA=true and HOSTED_PREVIEW=true; that hosted sample resets on reload and never calls a visitor's local Laravel server.

A shared API deployment needs PHP-capable hosting, a persistent database, HTTPS, authentication, branch policies, approved browser origins, and a configured frontend API URL. SQLite remains the exercised local database; MySQL/PostgreSQL migrations and operations need testing before a switch.

09 · Verification and next architecture steps

Run Flutter checks inside frontend and Laravel checks using the root helpers:

flutter analyze
flutter test
flutter build web --profile --dart-define=HOSTED_PREVIEW=true --dart-define=USE_DEMO_DATA=true --base-href /veritas_prototype-0.1/

.\scripts\artisan.cmd test

Tests cover HTTP serialization, server-confirmed saves, failed writes, refresh failure/retry, duplicate-tap prevention, REST persistence, report uniqueness, stock operations, validation, CORS, the environment gate, and the earlier navigation/layout scenarios.

Next steps: identity and role/branch authorization, audit history, durable submission/approval states, patient records, scheduling, transaction-level billing, pagination, concurrency policies, notification delivery, and backup and restore procedures. Installing a REST layer does not complete these broader clinic workflows.

Design System

Veritas Prototype 0.1 · Vista Care interface Implementation reviewed: 16 October 2026

Visual foundations, reusable components, responsive behavior, and motion rules for the clinic dashboard.

Related documents: Architecture · Product requirements · Workflows

01 · Brand identity and principles

The interface uses Vista Care and an owner-portal identity. The folder name, veritas_prototype 0.1, is a project label; a product-wide rebrand has not been implemented.

  • Use blue for navigation and primary actions, green for positive operational or financial context, and white surfaces for readable information.
  • Put important numbers before supporting explanations.
  • Group related information in rounded panels with generous spacing.
  • Make branch and date scope visible wherever totals or edits depend on them.
  • Use motion to explain navigation and acknowledge interaction.
  • Show operational alerts neutrally. A discrepancy prompts review; it is not an accusation.

The supplied design-system image informs this document's structure. Its pink palette, Inter typeface, and Lucide icons are example choices, not this project's implementation.

03 · Typography

The theme requests Segoe UI without bundling a font asset. Platforms without it can fall back to another font; identical typography across devices is not guaranteed. Sizes below are Flutter logical pixels.

Theme style Size Weight Letter spacing Role

Components also use 27/800 metric values, a 40/700 revenue hero amount, and 9–11 px metadata. Smaller styles require readability review; they are not an accessibility endorsement.

Use sentence case for actions. Reserve uppercase and wide tracking for short eyebrow labels. Pair amounts and counts with context: “patients today,” “last 7 days,” or “gross revenue (PHP).”

07 · Icons

Existing screens use Flutter's Material Icons, primarily outlined and rounded variants. Common sizes are 16–24 px; metric icons are 20 px. Keep stroke style and icon size consistent within a row. Icon-only actions need a tooltip or accessible label. Do not add a second icon library solely to imitate the reference image.

08 · Responsive behavior

The actual shell navigation breakpoint is 1000 logical pixels:

Width Shell
Below 1000 Five-destination bottom navigation
1000 and above 218 px sidebar, including inventory access

Main shell content has a maximum width of 1180; branch detail uses 1000 and inventory 1050. ResponsiveGrid calculates columns from available width and a default minimum card width of 160, up to four columns. Branch cards use a minimum of 260 and up to three columns. This is content-driven wrapping rather than a fixed tablet breakpoint.

Tabs are Home, Daily reports, Statistics, Revenue, and Branches. Inventory opens from alerts, shortcuts, branch details, or the sidebar. Selecting another tab resets the shared scroll position to the top.

Debug builds default to iPhone 16 Device Preview. Use --dart-define=DEVICE_PREVIEW=false to inspect the host's actual dimensions. Device Preview is not native iOS execution.

09 · Motion specification

Sources: app_motion.dart and TrendChart in clinic_ui.dart.

Interaction Implemented motion
Tab entry 650 ms; starts at 28% horizontal travel, 20 px vertical offset, scale 0.94 → 1 with easeOutBack overshoot
Entry opacity Fades in during the first 55% of progress
Tab exit 300 ms; opposite travel up to 14%, fade-out, scale toward 0.955
Direction Relative tab order; accounts for RTL
Grid entrance 620 ms; fade and 16 px upward settle; interval stagger capped at index seven
Chart reveal 800 ms; left-to-right clipping with easeOutCubic
Branch-card feedback 220 ms; press scale 0.98 / hover scale 1.008
Pushed pages Cupertino transitions across configured platforms

Motion uses Flutter/Dart. Outgoing tab content ignores pointer events and is excluded from semantics. Reduced-motion handling checks MediaQuery's disable-animations flag and the host's reduce-motion feature; tab, entrance, chart, and route effects are skipped or shortened, and hover/press transforms become neutral.

Do not introduce endless decoration, expensive blur transitions, or animation that delays saving. Reuse shared motion components.

10 · Accessibility and content rules

These are requirements to verify, not completed certification:

  • Support keyboard navigation, visible focus, and meaningful control labels.
  • Review muted text contrast against each actual background.
  • Test large text, small screens, and forms with the keyboard visible.
  • Do not communicate stock or expiry status using color alone.
  • Provide chart summaries; the custom painter does not currently expose a complete accessible data table.
  • Preserve tooltips and adequate touch targets.
  • Do not shrink essential labels merely to fit a card.
  • Show branch/date context before replacing a saved report.

Dates follow the Philippine clinic day (UTC+8). Money is displayed as rounded whole Philippine pesos. Explicit demo builds must identify sample data and reset-on-restart behavior; local API builds show a database-connected status.

11 · Review checklist

Check phone and desktop widths, iPhone safe areas, tab direction, rapid tab changes, scroll reset, validation, empty results, keyboard use, large text, and reduced motion. Existing tests exercise 320 and 1440 px layouts; further device and accessibility checks remain manual.

When changing tokens, breakpoints, or motion, update this document and the corresponding source together.

REST integration update - 18 October 2026

SaveDialog now provides pending, validation/error, and confirmed-save states. ClinicConnection provides startup loading, empty-branch, and retry screens. The header refresh action reloads persistent records. Existing tokens, layouts, and motion remain shared across API and explicit demo modes.

PRD.mdVERITAS · PROTOTYPE 0.1

Product Requirements Document

Veritas Prototype 0.1 · Centralized Multi-Branch Clinic Administration System Baseline: 16 October 2026 · Status: interactive owner-dashboard prototype

Defines the problem, intended users, current product behavior, and requirements for future clinic operations.

Related documents: Architecture · Design system · Workflows

01 · Product overview

Field Definition
Project Veritas Prototype 0.1
Current UI brand Vista Care
Purpose Help authorized clinic management understand branch performance and operational needs
Current users A simulated clinic owner; no authenticated user accounts
Intended reach Six branches with Pasig as the proposed central administration hub
Branches Laguna, Pasig, Caloocan, Parañaque, Quezon City, Valenzuela
Current platform Flutter application with Android and Chrome development usage
Current storage Laravel REST API with persistent local SQLite; explicit demo mode remains in-memory

The product should give management one place to compare visits, collections, expenses, reports, and medicine inventory. The broader vision includes controlled patient records, billing, doctor attendance, scheduling, and auditability.

02 · Problem and goals

Information spread across branches makes it difficult to know which reports are complete, where supplies need attention, and how performance compares. The original workflow also identifies the need to protect clinical information and coordinate doctors across locations.

Prototype goals

  1. Demonstrate an understandable overview of six branches.
  2. Let reviewers filter by branch and compare daily, seven-day, and thirty-day information.
  3. Demonstrate report entry/editing and inventory updates with immediate UI feedback.
  4. Show useful stock and expiry alerts.
  5. Provide responsive layouts and an iPhone screen preview for design review.

Production goals

Create durable, shared operations with server-enforced permissions, traceable changes, and reliable cross-branch coordination. Production goals are requirements for future work; they are not features delivered by this prototype.

Out of scope

A patient-facing portal, online patient self-service, payment-gateway integration, automated clinical decisions, and automated fraud accusations are outside the current scope. Individual medical records and actual payments must not be inferred from aggregate report screens.

03 · Users and permissions

The following roles come from the intended clinic workflow. None of these permissions is currently enforced by the application.

Role Intended responsibility
Owner / CEO / main administrator Authorized oversight across all six branches; users, roles, reports, alerts, audit review
Pasig branch manager Pasig operations; central access only if separately authorized
Other branch manager Operations and reports for the assigned branch
Reception Basic registration, patient identity search, appointment creation
Billing staff Services, payments, refunds, sales reporting; no medical notes
Inventory staff Stock movements, requests, expiry and adjustments; no clinical records
Nurse / authorized staff Minimum information required for assigned clinic service
Doctor Authorized clinical history and clinical notes; billing only with separate permission

Owner visibility of operational data does not automatically grant unrestricted access to clinical notes. Production policies must define sensitive-data access by purpose, role, resource, and branch.

04 · Current functional requirements

“Implemented” below means present in the inspected source, not deployed as a production service.

ID Feature Current behavior / acceptance criterion
C01 Owner navigation Five sections are reachable on mobile and desktop; inventory is reachable from relevant shortcuts
C02 Branch scope Selecting a branch limits dashboard views and related totals; “All branches” restores combined scope
C03 Overview Show daily visits, collections, branch summaries, and inventory attention items from sample data
C04 Daily reports Select today or a past date within the picker range; view and create/edit branch reports
C05 Report validation Patients are nonnegative integers; revenue/expenses are finite nonnegative numbers; notes are optional
C06 Report replacement Saving the same branch/date replaces its report rather than double counting it
C07 Statistics Switch between seven and thirty days; show visit totals, averages, comparisons, and sample staff ratings
C08 Revenue Switch today/seven/thirty days; show gross, expenses, net, and guarded net-margin calculation
C09 Branch details Show address, daily target, visits, inventory overview, trend, and sample staff information
C10 Inventory search Search medicine or branch text; switch all batches / needs attention
C11 Batch creation Require a medicine name, nonnegative integer quantity and threshold, unit, branch, and expiry
C12 Stock changes Add a positive whole-number restock or set a nonnegative corrected on-hand quantity
C13 Alerts Flag quantity at/below threshold, expired dates, and expiry within 60 days
C14 Responsive motion Use responsive navigation and animated tab/card/chart transitions with reduced-motion handling
C15 Device preview Debug starts with an iPhone 16 simulation; an opt-out flag restores host dimensions

Batch units are vials, tablets, capsules, bottles, or boxes. The batch date picker accepts today through approximately ten years ahead. Different expiry deliveries should use separate batches.

Daily reports currently contain patient count, gross revenue, operating expenses, and notes. The “Submitted” label is a stored report display state; it is not evidence of manager approval or a formal submission workflow. API saves now wait for server confirmation.

05 · Planned functional requirements

These preserve the original workflow's intended scope. P03 is partially implemented locally; production identity, policies, conflict handling, and deployment remain open.

ID Priority Requirement and acceptance condition
P01 Foundation Authenticate users; deny invalid access and record the outcome
P02 Foundation Enforce role, branch, module, and action checks on every server request, including direct resource access

Related documents: Architecture and API contract · Setup · Requirements

01 · Current scope

The six branches are Laguna, Pasig, Caloocan, Parañaque, Quezon City, and Valenzuela. Pasig remains the intended central administration hub.

Implemented locally Still planned
Flutter dashboard with Laravel HTTP requests Login and server-enforced user/branch permissions
Persistent daily reports Formal submission, review, approval, and correction history
Persistent medicine batches and quantity changes Transfers, movement ledger, purchase requests
Branch metadata and sample staff ratings User administration and live attendance

Laravel owns the database. Flutter owns presentation, forms, navigation, branch display filters, and calculated dashboard summaries.

The API currently has a local/testing environment restriction and no authenticated roles. Do not treat branch selection as authorization.

02 · Prepare the local system

From the repository root:

.\scripts\artisan.cmd migrate
.\scripts\artisan.cmd db:seed --class=ClinicDemoSeeder
.\scripts\artisan.cmd serve --host=127.0.0.1 --port=8000

In another terminal:

cd frontend
flutter pub get
flutter run -d chrome

The explicit demo seeder creates sample branches, reports, and batches. Rerunning it preserves saved quantities and existing reports. Normal Flutter restarts fetch stored data instead of recreating it.

An Android emulator uses 10.0.2.2 to reach the development computer. For another host use --dart-define=API_BASE_URL=http://HOST:8000/api/v1; server binding and network access must also allow that host.

03 · Application startup and navigation

  1. Local app startup uses the Laravel API by default.
  2. Show a connecting state while loading the three resource collections.
  3. If a request fails, show an error and Retry; do not substitute demo data.
  4. If no branches exist, show an empty setup state.
  5. Once loaded, show Home, Daily reports, Statistics, Revenue, and Branches.
  6. Inventory opens through alerts, shortcuts, branch details, or the sidebar.
  7. Branch selection narrows displayed data; the API currently returns all prototype branches.

Changing tabs preserves the existing motion and resets the shared scroll position to the top. Refresh fetches other users' committed changes. If refresh fails after a successful load, the current snapshot remains visible and the refresh error is reported.

04 · Create or replace a daily report

  1. Open Daily reports and choose a date; the UI allows today and the previous 365 days.
  2. Create a report or edit an existing one.
  3. Choose a branch for creation. Editing keeps its branch fixed.
  4. Enter whole-number patient count, revenue, expenses, and optional notes.
  5. Run local validation, then show a saving state with repeat submission disabled.
  6. Send PUT to /api/v1/branches/{id}/reports/{YYYY-MM-DD}.
  7. Laravel validates the values and report date.
  8. Persist one report for that branch/date; replace its values if it already exists.
  9. Return the stored report as JSON.
  10. Update Flutter's cache and aggregates, then close the dialog.

Patient count must be a nonnegative integer. Money must be nonnegative, within the supported range, and have no more than two decimal places. The server rejects future dates. Validation failures return 422 and keep the form open with entered data and an error message.

The “Submitted” badge currently means a stored report exists. It does not mean a manager has approved it or a separate submission deadline was met. Refreshing/reopening the app reads the persisted report.

05 · Create a medicine batch

  1. Open inventory and select Add medicine.
  2. Choose branch, medicine name/strength, quantity, unit, threshold, and expiry.
  3. Validate locally; a missing expiry keeps the form open.
  4. POST to /api/v1/medicine-batches using the branch's database ID.
  5. Laravel validates branch existence and field values.
  6. Insert the batch and return 201 with its assigned ID.
  7. Add the returned batch to Flutter's cache and recalculate attention counts.

Units are vials, tablets, capsules, bottles, or boxes. Quantity and threshold are nonnegative integers. The server rejects past expiry for new batches. A different-expiry delivery belongs in a separate batch.

Cancelling before submission leaves data unchanged. A failed response retains the form; successful creation persists across app restarts.

06 · Restock or correct inventory

  1. Search medicine/branch and choose all batches or needs attention.
  2. Open Restock to add a positive quantity, or Adjust stock to set the current count.
  3. Send PATCH to /api/v1/medicine-batches/{id}.
  4. Laravel validates the operation and quantity.
  5. Inside a transaction, read/lock the current batch and apply the operation.
  6. Return the stored batch.
  7. Replace the cached record and recalculate alerts.
Operation Request Result
Restock operation=restock; quantity=10 Add 10 to current server quantity
Correction operation=set; quantity=25 Set on-hand quantity to 25
Invalid quantity/operation Invalid JSON field values 422; no committed quantity change
Missing batch Unknown resource ID 404; show error

Corrections and restocks currently have no approval reason, movement ledger, or audit record. Restocks are transactional; stock corrections and report edits do not yet have version-conflict handling.

07 · Alerts and totals

Flutter recalculates these values from loaded records:

Rule Behavior
Clinic day Philippine calendar date, UTC+8
Low stock Quantity at or below threshold
Expired Expiry before the clinic day
Expiring soon Not expired and within 60 days, including today
Attention Any low/expired/expiring condition
Status priority Expired → Low stock → Expiring soon → Healthy
Net revenue Report collections minus operating expenses
Net margin Net / gross × 100; guard zero gross

Restocking does not change expiry. A restocked batch may remain in the attention list because it expires soon. There is no delivered notification service; these are in-app operational indicators.

08 · Errors and synchronization boundaries

Situation Current response
API unavailable at startup Connection screen and Retry
Refresh fails Retain last snapshot and show the error
Invalid form Keep entered values and display validation feedback
Save pending Disable repeat submission and editing
Server rejects save Keep dialog open; do not change cached records
Missing resource Display the API error; refresh to retrieve current data
Timeout Display error; verify server state before retrying uncertain writes
Another client writes Refresh or reopen to fetch committed changes
API in production environment Local-only gate returns 503
Explicit demo build Use in-memory data; reset on restart/reload

There is no automatic polling, offline write queue, websocket synchronization, or exactly-once retry mechanism. A timeout can occur after the server has committed a request. Check the resulting data before repeating batch creation or a restock.

09 · Hosted demo versus shared backend

GitHub Pages builds with USE_DEMO_DATA=true; it shows the design with sample data and does not contact the local API. It cannot run Laravel.

Groupmates can clone the repository and run their own local databases. Those databases are separate. To share data, clients must intentionally connect to the same reachable API/database; authentication and permissions must be implemented before public deployment.

10 · Secure clinic workflows — planned

The original broader operating requirements remain part of the product direction. The REST integration above does not implement these processes.

A. Secure login and zero-trust access

Verify credentials, identity, role, assigned branch, module, resource, and action for every request. Deny unauthorized operations and record relevant access attempts. Apply minimal field access; a successful login does not authorize all later requests.

Role Intended scope
Owner / CEO / authorized main administrator Authorized all-branch operations, user/role management, reporting and audit oversight
Pasig manager Pasig operations; central access requires additional permission
Other branch manager Assigned-branch operations and permitted approvals
Reception Basic identity/registration and appointments
Billing Payments, sales, refunds; no private clinical notes
Inventory Stock events, transfers, expiry and history; no clinical records
Nurse / authorized staff Minimum information required for assigned services
Doctor Authorized clinical history and permitted clinical note changes; billing only with separate permission

B. Patient records and cross-branch access

Search centralized patient identities and prevent duplicates. Create or retrieve the identity, then apply role/branch field restrictions. Reception sees registration details; nurses see permitted service information; doctors see authorized clinical records and may make permitted note corrections.

Additional cross-branch information requires a request, authorized review, minimal release, or a recorded denial reason. Audit relevant record access, changes, requests, decisions, and releases.

C. Doctor attendance and scheduling

Record QR time-in/time-out, timestamp, doctor, assigned/actual branch, and attendance status. Managers confirm duty branch. Compare appointment branch, time, assignment, and availability.

Confirm compatible appointments. For conflicts, notify branch management and authorized Pasig administrators; human reviewers assign another doctor, reassign/reschedule, or notify the patient through approved staff channels. Record the action, reason, appointment status, and audit context.

D. Inventory transfers and replenishment

Record stock-in/out, usage, expiry, corrections, and movement history. Review low-stock and discrepancy alerts. If another branch can supply stock, submit and approve/deny a transfer; otherwise request replenishment.

Fulfillment must preserve batch expiry and update both inventories atomically without negative available stock. Keep request, decision, movement, and adjustment history. An alert must never automatically accuse a person of fraud or misconduct.

E. Sales, billing, and refunds

Billing staff record services, payments, and branch. Refunds need a reason and authorized manager review. Preserve the original transaction and audit approval/rejection and financial changes. Billing access is separate from medical-note access.

F. Reviewed daily branch submission

Collect patient count, completed services, sales/payments, refunds, inventory movements, low stock, staff attendance, schedule status, and conflicts. Managers review completeness and request corrections.

Submit after closing, preferably after 5 PM clinic time; persist submission identity/time and later corrections. The preferred time is a process guideline until a formal cutoff policy is agreed.

G. Pasig central monitoring

Authorized management reviews consolidated/branch reports, sales, visits, returning patients/follow-ups, attendance, conflicts, inventory, fast-moving supplies, and access/discrepancy alerts when those modules exist. Inspect supporting records, assign follow-up, and track resolution and audit history.
